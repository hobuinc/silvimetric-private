### Wall time and nominal vCPU efficiency

The 12:29–20:22 UTC gross interval (7 h 53 min) is **not** a clean throughput sample. Nineteen blocks published by 15:39; the next did not publish until 19:58 while the release/cost/timeout diagnostics held the remaining work. After the remaining 53 leaves were released at 19:48–19:53, they published 2,032,068,724 receipt points by 20:16 and the finalizer finished at 20:22. Those 53 stages logged 33,640.5 aggregate stage seconds over roughly 28 minutes, about 20 concurrently active four-vCPU jobs on average (80 assigned stage vCPUs), far below the 480-vCPU fleet ceiling. Across all 72 successful stages, measured source read/PDAL time was 31,077.8 seconds of 42,674.2 application stage seconds (73%); metrics were 9,310.9 seconds (22%).

AWS Batch reports 74 stage jobs (72 successful, two failed) totaling 46,554.9 job-runtime seconds at four vCPUs; 72 publisher jobs totaled 1,729.3 seconds at four vCPUs. With the approximately 293-second two-vCPU finalizer, that is **53.8 assigned job-vCPU-hours**, or **49.2 million receipt points per assigned vCPU-hour**. This excludes EC2 host slack, boot/scale-down tails, and other control-plane work; it is not billed instance usage.

The earlier Dask 2.65B calibration used 14 `m9g.8xlarge` workers and one scheduler, failed after 117 of 121 stages, then required a second fleet to recover the remaining four. Its documented 8.3925 + 4.4718 EC2 instance-hours across those 15-host fleets correspond to approximately **384 worker-vCPU-hours**, or **6.89 million points per reserved worker-vCPU-hour**. Its $20.15 on-demand EC2 estimate covers both attempts. This is an operational comparison of two imperfect attempts, **not a same-algorithm speedup**: Dask used a different output projection, 0 m rather than 20 m collar, a different processing-core grid, and larger on-demand hosts. Its 977.7-second successful *recovery* reused 117 stages and is not a from-scratch 2.65B wall time. For context, the clean earlier Dask 7.65B run achieved approximately 23.2 million points per reserved worker-vCPU-hour on a different footprint.

On 2026-09-24, AWS Spot history for the relevant `us-west-2` Graviton types was approximately $0.015–$0.022 per physical vCPU-hour, versus the AWS Price List's $1.56544/hour ($0.04892/vCPU-hour) for on-demand `m9g.8xlarge`. A useful Batch compute model is `assigned stage vCPU-hours / host packing × Spot $/physical vCPU-hour`, plus on-demand publisher/control hosts, launch/idle, EBS, S3, and networking. At an *illustrative* 75% packing, the measured stage jobs imply about $1.0–$1.5 of occupied Spot host time; this is not the total bill. Cost Explorer currently reports zero tagged cost for this same-day RunId and marks it estimated, so a billed per-run comparison is not yet available. The $41.10 admission reservation above is neither billed EC2 cost nor evidence that Batch itself costs $41.

## Quality findings

1. Published stage receipts total **2,647,868,723 points**, but a GDAL read of the complete bounded `count` raster and an independent TileDB-Py read both sum to **2,451,307,927**. The difference is **196,560,796 points (7.423% of receipts)**. The raster window is 484 × 478 20 m cells and covers every published block. The 72 published block rectangles overlap in 34,828 cells; receipt cell counts exceed the canonical populated-cell count by 15,685. The publisher's one-rectangle dense write for each irregular block fills its holes with zeros, overwriting previously published cells. Its immediate per-block signature check can pass because the overwritten neighbor is outside the stage's populated footprint. A new local L-shaped-block regression proves the corrected per-macro publishing behavior.
2. The L-moment implementation used NumPy `int64` multiplication for its fourth-moment denominator. At 55,111 points per cell this overflows. The canonical `count` array has **2,372 populated cells at or above that threshold** (1.194% of its 198,597 populated cells). Their L4 and L-kurtosis products are suspect; a sampled dense block produced implausibly large L4 values. The code now normalizes each weight before multiplying, with a 60,000-point regression test. Other metrics have not yet had a complete post-seal audit.

## Corrective work and release gate

- The publisher now partitions an immutable stage by its exact, non-overlapping planned macro cores and writes each macro rectangle separately. Canonical reconciliation compares only the stage's owned cells, allowing unrelated populated cells in an irregular block's bounding box. A crash partway through these writes remains recoverable by replaying the immutable stage.
- Batch completion now sums the canonical `count` attribute in bounded row chunks and refuses to issue a `build_published` receipt when it differs from the published-stage receipt total. This prevents an overwritten array from being sealed as successful on a future build.
- This sealed array was produced before these fixes and is **not repaired by them**. Repair requires a fresh, uniquely identified build and independent count/metric/GDAL/extract checks. The old stages also contain overflowed L-moment values, so simply replaying them cannot make the product valid.
- Do not start another 2.65B run merely because this build sealed. First verify the corrected publisher and metric calculations in a bounded S3 canary, build and pin the tested container image, estimate the new write-fragment/finalization cost, and verify the new run stays under the $50 per-run limit. Preserve this build and its reports until the replacement is accepted.
